# Localization release gate - Build 09 preparation

This is a development plan, not a list of approved languages. The live site remains EN, DE, ES and Simplified Chinese, with 40 pages each. No untranslated or machine-only language page should be made public.

1. Finish the country, competitor and scoring evidence in `LANGUAGE-MARKET-RESEARCH.md`; identify uncertainty and sensitivity to support capacity. Ask the owner to approve a ranked selection and confirm who can reliably answer each language.
2. For each approved language, create a separate unpublished catalog for every canonical source entry (`app/i18n/source.json`) and translate all manually maintained content such as `faq-additions.tsx`, `local-coordination.tsx`, contact fallback, copy controls and structured business information. Do not put private inquiries through unapproved translation services.
3. Have independent qualified reviewers check medical, privacy and legal text. Record a durable review reference, source version and support workflow; do not represent automatic translation as professional review.
4. In an isolated branch/export implement locale route segments, 40 pages, metadata, canonical and reciprocal hreflang, sitemap, switcher labels, email fallback, accessible directionality and responsive typography. For RTL locales test document `dir`, visual order, mixed-script email addresses, keyboard behavior and content ordering. Do not automatically redirect based on IP.
5. Before merging, run `scripts/check-locale-candidate.mjs manifest.json isolated-export-directory`. Its manifest needs `locale`, `catalog` (path relative to the manifest), `canonicalSourceSha256`, `manualSourceSha256`, `ownerApproved`, `specialistReviewed`, `contactSupportVerified`, `manualComponentsReviewed`, and a nonempty `reviewEvidence` reference. The manual hash is SHA-256 over the exact sequence `filename`, NUL, file bytes for `faq-additions.tsx`, `local-coordination.tsx`, `consultation-email-fallback.tsx` and `copy-email.tsx`, in that order. The gate checks only structural completeness and evidence fields; it cannot itself authenticate a reviewer, verify every sentence, test accessibility or authorize production.
6. Re-run content hashes, locale-navigation, mobile, a11y, SEO and contact checks. Verify all language links lead to real localized pages and all static content is readable without JavaScript. Publish only after explicit production authorization and only after real receiving channels are verified.

Existing code uses the hard-coded `locales` tuple in `app/i18n/locale.ts` and separate Next.js route directories. Merely adding a code there is insufficient: locale layouts, dictionaries, manually maintained copy and all route variants also need updating. The gate does not alter production configuration.
