# Localization release gate - Build 09 preparation

The owner requested Russian, Arabic, French, Bengali, Hindi, Brazilian Portuguese, Indonesian, Korean, Japanese and Vietnamese in addition to the four existing languages. The live site remains EN, DE, ES and Simplified Chinese, with 40 pages each. The ten requested additions remain inactive until ready.

1. Preserve the requested list and the owner's confirmed customer-support languages: English and Chinese. The language selector must not imply that support is available in other languages.
2. For each approved language, create a separate unpublished catalog for every canonical source entry (`app/i18n/source.json`) and translate all manually maintained content such as `faq-additions.tsx`, `local-coordination.tsx`, contact fallback, copy controls and structured business information. Do not put private inquiries through unapproved translation services.
3. Have independent qualified reviewers check medical, privacy and legal text. Record a durable review reference, source version and support workflow; do not represent automatic translation as professional review.
4. In an isolated branch/export implement locale route segments, 40 pages, metadata, canonical and reciprocal hreflang, sitemap, switcher labels, email fallback, accessible directionality and responsive typography. For RTL locales test document `dir`, visual order, mixed-script email addresses, keyboard behavior and content ordering. Do not automatically redirect based on IP.
5. Before merging, run `scripts/check-locale-candidate.mjs manifest.json isolated-export-directory`. Its manifest needs `locale`, `catalog` (path relative to the manifest), `canonicalSourceSha256`, `applicationSourceSha256`, `reviewedCatalogSha256`, `ownerApproved`, `specialistReviewed`, `contactSupportVerified`, `manualComponentsReviewed`, and a nonempty `reviewEvidence` reference. `canonicalSourceSha256` and `reviewedCatalogSha256` are SHA-256 of the raw file bytes; `applicationSourceSha256` is calculated by `applicationSourceHash()` in `scripts/locale-source-hash.mjs`, covering all application TypeScript, CSS and JSON. The gate checks structural completeness, hashes and evidence fields; it cannot authenticate a reviewer, verify every sentence or test accessibility.
6. Re-run content hashes, locale-navigation, mobile, a11y, SEO and contact checks. Verify all language links lead to real localized pages and all static content is readable without JavaScript. Publish requested changes when ready and after real receiving channels are verified.

Existing code uses the hard-coded `locales` tuple in `app/i18n/locale.ts` and separate Next.js route directories. Merely adding a code there is insufficient: locale layouts, dictionaries, manually maintained copy and all route variants also need updating. The gate does not alter production configuration.

For isolated routing and direction experiments only, run `node scripts/preview-locale-scaffold.mjs ar` after generating the normal export. It creates 40 explicitly untranslated test pages under `../translation-work/route-fixtures/ar/`, including `noindex` and a robots exclusion. It refuses to overwrite an existing fixture and cannot write into the application checkout. Serve the parent fixture directory locally if needed. These pages are not a translation, a candidate release, or a replacement for real localized Next.js routes; never deploy them. Verify the generator and release gate with `node scripts/test-locale-scaffold.mjs` and `node scripts/test-locale-gate.mjs`.
